# Как я подошёл к реализации

**Исполнитель:** Vladislav  
**Модуль:** `local.crmassigncascade`  
**Версия:** 2.0.4

Этот документ — не формальное описание классов, а краткая история принятия решений: с чего я начал, почему выбрал именно такую структуру и как в итоге работает решение.

## С чего я начал

Сначала я разложил тестовое задание на несколько независимых задач. Нужно было встроиться в штатный список компаний, дать администратору выбрать нового ответственного и наблюдателей, при необходимости применить изменения к связанным CRM-элементам, а саму тяжёлую обработку убрать из HTTP-запроса.

Сразу стало понятно, что выполнять весь каскад по AJAX нельзя. Даже несколько компаний могут иметь десятки сделок, контактов и элементов смарт-процессов. Если обрабатывать всё в браузерном запросе, мы получим таймауты и зависимость от открытой вкладки. Поэтому я разделил решение на две части: HTTP только создаёт задание, а cron-worker выполняет его независимо от пользователя.

## Как я спроектировал хранение данных

Дальше я продумал, что именно нужно хранить в базе, чтобы операция могла продолжиться после сбоя и чтобы всегда было понятно, что именно изменялось.

В результате получилось три таблицы.

### 1. `b_local_crm_assign_job`

Это само задание. Здесь хранится, кто его запустил, кого нужно назначить ответственным, какие наблюдатели выбраны, режим `добавить/заменить`, какие связанные типы нужно обрабатывать и общий статус задания.

Одна запись в этой таблице соответствует одному запуску пользователем.

### 2. `b_local_crm_assign_job_company`

Эта таблица хранит точный список компаний задания и одновременно является очередью для cron.

Я специально не оставляю режим «Для всех» в виде живого фильтра на всё время выполнения. В момент создания задания backend получает текущий CRM-фильтр, вычисляет компании и фиксирует их ID в таблице. После этого состав задания уже не зависит от того, что позже изменилось в CRM или в фильтре пользователя.

Это также решает случай с выбранными строками: если выбрана одна компания, в очереди должна появиться ровно одна строка. Перед commit backend сверяет фактическое количество с количеством, которое подтвердил интерфейс. Если числа расходятся, создание задания откатывается.

### 3. `b_local_crm_assign_log`

Это журнал каждого CRM-элемента. В нём сохраняется:

- кто запустил изменение;
- к какой компании относится обработка;
- тип и ID CRM-элемента;
- старый и новый ответственный;
- старые и новые наблюдатели;
- итоговый статус;
- сообщение об ошибке или причине пропуска;
- время обработки.

Журнал нужен не только для отчёта. Он также защищает от повторной обработки. Например, один контакт может быть связан сразу с двумя выбранными компаниями. Уникальный индекс по `JOB_ID + ENTITY_TYPE_ID + ENTITY_ID` не позволяет изменить его дважды в рамках одного задания.

## Какие блокировки я выбрал

Я исходил из того, что для этого кейса не нужна тяжёлая инфраструктура с Redis, RabbitMQ или постоянно работающим daemon.

Cron запускает короткий CLI-worker раз в минуту. В `worker.php` используется `flock`, чтобы два обычных запуска одного worker-а не выполнялись одновременно.

Дополнительно строка компании забирается из очереди атомарным `UPDATE queued -> processing`. Это защита на уровне БД: даже если второй consumer всё-таки появится, одну строку очереди одновременно не должны забрать два процесса.

Если PHP аварийно завершился и строка осталась в `processing`, спустя заданный интервал она возвращается в очередь. Уже обработанные CRM-элементы определяются по журналу, поэтому повторный запуск не должен дублировать изменение.

Я сознательно не оборачивал весь каскад одной компании в одну длинную SQL-транзакцию. `CRM UpdateOperation` может запускать историю, timeline, роботов и бизнес-процессы. Держать транзакцию вокруг большого количества таких операций было бы тяжело для базы и не давало бы честной гарантии отката всех внешних эффектов. Поэтому здесь используется короткая транзакция для создания задания и идемпотентная обработка для CRM.

## Как я встроился в список компаний

Я не стал копировать или изменять штатный компонент. Такой способ сильно зависит от версии Bitrix24 и усложняет обновления.

Вместо этого модуль на странице компаний подключает небольшой JS-адаптер. Он получает уже существующий `main.ui.grid`, его `ActionsPanel` и добавляет пункт «Сменить ответственного и наблюдателей» в штатный список групповых действий.

Выбранные строки читаются через API Grid. Режим «Для всех» используется только когда штатный checkbox действительно отмечен. В сомнительной ситуации модуль выбирает безопасный вариант и работает только с явно выбранными ID.

Для выбора ответственного и наблюдателей используется штатный `BX.UI.EntitySelector.TagSelector`, поэтому визуально и по поведению поле остаётся привычным для Bitrix24.

## Как работает cron

После создания задания браузер больше не нужен.

Cron запускает `bin/worker.php`. Worker берёт ограниченное количество компаний и имеет ограничение по времени одного запуска. Это сделано, чтобы фоновая задача сама не создавала длительную постоянную нагрузку на портал.

Обычная последовательность такая:

1. найти следующую строку `queued`;
2. атомарно перевести её в `processing`;
3. загрузить параметры job;
4. изменить компанию;
5. обработать только выбранные пользователем связанные типы;
6. записать результат каждого CRM-элемента в журнал;
7. отметить компанию как `done` или поставить её на повторную попытку;
8. после завершения всех компаний закрыть job и отправить отчёт.

## Как меняется CRM

Прямых `UPDATE` по таблицам CRM нет.

Для каждого элемента я получаю штатную Factory, Item и запускаю:

`Factory -> getUpdateOperation($item, $context) -> launch()`.

Перед запуском, если соответствующие методы доступны в текущей коробке, включаются история, before/after-save actions, automation и BizProc. Это нужно, чтобы изменение проходило через штатный CRM lifecycle, а роботы и бизнес-процессы, настроенные на изменение элемента, могли отработать.

Если CRM-тип не поддерживает наблюдателей, модуль не пытается искусственно записывать несуществующее поле: меняется только ответственный, а информация об этом остаётся в журнале.

## Сделки и смарт-процессы

Сделки и смарт-процессы в финальных стадиях не изменяются. Финальность определяется через semantics стадии, а не через захардкоженные `STAGE_ID`.

Со смарт-процессами пришлось отдельно учитывать различия коробок. На одной из тестовых конфигураций `DynamicTypesMap` в CLI возвращал пустой список, хотя СП существовали. Поэтому список типов определяется двумя штатными D7-способами: через карту типов и через D7-таблицу типов.

Связанные с компанией элементы СП сначала ищутся через CRM `RelationManager`, что соответствует фактическим связям, видимым в интерфейсе «Связи». Для старых вариантов оставлен fallback по полю `COMPANY_ID`.

## Что происходит после запуска

После успешного создания задания пользователь сразу получает штатное уведомление: «Задача по смене поставлена в очередь».

Окно прогресса не используется — операция должна быть независимой от браузера.

Когда cron полностью завершил обработку, инициатор получает системное уведомление Bitrix24 с итогом. Например:

```text
Смена ответственного завершена
Компании: обновлено 8 из 8.
Связанные элементы не выбраны.
```

или:

```text
Смена ответственного завершена
Компании: обновлено 8 из 8.
Связанные элементы:
Сделки: обновлено 8 из 10, пропущено 2.
Контакты: обновлено 10 из 10.
```

Уведомление сохраняется в штатном списке IM. Для активного браузера дополнительно используется Pull, потому что cron работает из CLI и у него нет обычного page epilogue веб-запроса.

## Почему решение находится в `/local/modules`

Я выбрал локальный модуль, а не набор файлов в `php_interface`, потому что модулю нужны собственные таблицы, install/uninstall lifecycle, namespace, обработчик события, JS и CLI-worker.

Код не изменяет файлы `/bitrix`. Это сохраняет границу между кастомной логикой и ядром и уменьшает количество проблем при обновлении платформы.

## Что получилось в итоге

В финальном варианте пользователь работает со штатным списком компаний и привычными элементами интерфейса Bitrix24. HTTP только фиксирует команду пользователя. Точный список компаний сохраняется в БД, cron обрабатывает его небольшими порциями, каждое изменение проходит через D7 CRM Operation и записывается в журнал, а после выполнения пользователь получает системный отчёт.

Для меня ключевым критерием было не просто «поменять поле», а сделать так, чтобы массовая операция была контролируемой: не зависела от вкладки браузера, не теряла scope задания, могла продолжиться после сбоя и оставляла понятный след в журнале.
